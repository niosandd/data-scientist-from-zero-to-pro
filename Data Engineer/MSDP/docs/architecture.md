# MSDP — как это устроено

Пет-проект, в котором я собирал ingestion-платформу с нуля: несколько источников, Kafka, NiFi, Bronze-слой и нормальный мониторинг. Ниже — как данные ходят по системе и зачем каждый кусок.

---

## Картина целиком

```text
 API (ISS)     PostgreSQL      FTP / HTTP
     │              │              │
     ▼              ▼              ▼
 Python         Pull / CDC        NiFi
 Producer
     │              │              │
     └──────────────┼──────────────┘
                    ▼
                 KAFKA
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      Consumer            NiFi / скрипты
          │                   │
     ┌────┴────┐              │
     ▼         ▼              ▼
  MongoDB   Parquet        Parquet
 (оперативка) (Bronze)
```

Сверху — источники. Посередине Kafka как буфер. Снизу хранилища: Mongo для оперативных запросов и Parquet как сырой слой озера.

Отдельно крутится мониторинг: Prometheus, Grafana, Loki. Он не в основном пайплайне, но без него стек слепой.

## Четыре реальных потока

### 1. Координаты МКС в реальном времени

Публичный API отдаёт lat/lon раз в несколько секунд.

`iss_producer.py` забирает JSON и кидает в топик `iss-position`.  
`iss_consumer.py` читает топик и делает две вещи:
- пишет в MongoDB (чтобы можно было быстро посмотреть последние точки)
- копит батч и сохраняет Parquet в `storage/bronze/iss/`

Зачем оба хранилища: Mongo — «что сейчас», Parquet — «что было за день/неделю» для дальнейшей обработки.

### 2. Выгрузка из Postgres (pull)

Классика: скрипт сам ходит в базу.

`postgres_pull.py` читает `raw.events`. Есть watermark по `updated_at` — при следующем запуске забираются только новые строки, а не вся таблица заново. Результат — Parquet в `bronze/postgres_events/`.

### 3. CDC через триггеры

Чтобы не опрашивать таблицу по кругу, на `raw.events` висит триггер. Любой INSERT / UPDATE / DELETE пишет строку в `raw.events_cdc`.

`cdc_to_kafka.py` читает эту таблицу с watermark по `cdc_id`, отправляет события в Kafka (`cdc-events`) и параллельно кладёт Parquet. Так получается и стрим изменений, и файл для озера.

### 4. NiFi

Три сценария на одном canvas:

- **HTTP** — `InvokeHTTP` ходит в API ISS, `PutFile` пишет JSON в `bronze/nifi_iss/`
- **FTP** — `ListFTP` + `FetchFTP`, дальше либо файл, либо `PublishKafka` в топик `nifi-events`
- **SQL** — `ExecuteSQL` через `DBCPConnectionPool` забирает данные из Postgres и тоже кладёт в Bronze

NiFi удобен, когда хочется собрать пайплайн мышкой и сразу видеть, где застрял flowfile. Python-скрипты — когда нужна точная логика (watermark, батчи, свои правила).

## Куда складываются данные

```text
storage/
├── bronze/                 ← сырьё, почти без правок
│   ├── iss/
│   ├── postgres_events/
│   ├── cdc_events/
│   ├── nifi_iss/
│   ├── nifi_ftp/
│   └── nifi_postgres/
├── silver/                 ← пока пусто, под очистку и нормализацию
└── gold/                   ← под витрины, когда дойдём
```

Идея простая: сначала сохранить «как пришло», потом уже чистить и агрегировать. Если на этапе Bronze что-то сломалось — всегда можно переиграть трансформацию, не дёргая источники заново.

## Что крутится в Docker

Одна сеть `msdp-net`, всё ходит друг к другу по именам сервисов.

| Группа | Контейнеры |
|--------|------------|
| Стриминг | zookeeper, kafka, producer, consumer |
| Базы | postgres, mongo |
| Ingestion UI | nifi, nifi-registry, ftp |
| Мониторинг | prometheus, grafana, loki, promtail, alertmanager, cadvisor, kafka-exporter |
| Прокси | nginx |

На ноуте с 8 GB RAM поднимается нормально. NiFi самый тяжёлый — если будет туго, его можно не стартовать.

## Зачем так, а не иначе

- **Несколько способов загрузки** — чтобы не учить один паттерн. API, pull, CDC и NiFi решают разные задачи.
- **Kafka в центре** — producers не знают, кто читает. Можно добавить ещё одного consumer, не трогая producer.
- **Parquet с первого дня** — колоночный формат, сжатие, нормально дружит с Spark/Pandas потом.
- **Watermark** — без него инкрементальные загрузки быстро превращаются в полный scan таблицы.
- **Мониторинг сразу** — когда пайплайн падает в 3 ночи, хочется увидеть это на графике, а не в логах контейнера.

## Что сознательно не делал

- Silver/Gold слои — задел есть, логики пока нет.
- Airflow / оркестрация по расписанию — скрипты запускаются руками или через `docker compose run`.
- Схема эволюции Avro/Schema Registry — для учебного объёма JSON хватает.
- Отдельные exporter'ы для Postgres и Mongo — в Prometheus они сейчас DOWN, и это ок: без exporter'ов `/metrics` там нет.

Когда понадобится — добавится. Сейчас цель была собрать рабочий контур end-to-end, а не enterprise-платформу.
